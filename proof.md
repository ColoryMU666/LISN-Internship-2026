### Pourquoi il n'est pas possible de se retrouver avec un paquet vérolé si on a demandé un paquet "classique" (par exemple, se retrouver avec un [faux pandas](https://gitlab.dsi.universite-paris-saclay.fr/matthieu.urios/testMaliciousPackage) si on a demandé pandas en faisant `uv add pandas`).

#### Un peu de mise en contexte avec un exemple concret :

Nous nous penchons sur le cas où une personne demande le téléchargement dans le cache partagé d'un un faux pandas depuis un repo git. La crainte est qu'une fois ce pandas vérolé est mis dans le cache, les autres utilisateurs qui demanderaient à inclure pandas dans les dépendances de leur projet se retrouvent à utiliser le paquet vérolé car uv irai chercher le faux pandas dans le cache au lieu de télécharger le vrai pandas depuis une source sure (par exemple pypi).

Nous allons prouver pourquoi cela ne peux pas arriver.  

#### Un peu d'explications sur comment uv structure son cache :

Comme on peut le lire [ici](https://docs.astral.sh/uv/concepts/cache/#cache-versioning) le cache uv est séparé en plusieurs buckets (ex : `archive-vX`, `git-vY` où X et Y sont les numéros de version du bucket en question). <br><br> 
Les paquets téléchargés depuis un repo git sont mis dans le bucket `git-vY` dans le dossier checkout/**\<repo_ident>**/**\<short_commit_sha>**. **\<repo_ident>** est un hash généré par uv à partir de l'url du repo spacifié dans la commande de demande du paquet. **\<short_commit_sha>** est une chaine de caractère obtenue en prennant les huits premiers caractère du SHA (Secured hashing Algorithm) du commit à partir duquel on souhaite installer notre paquet (par défaut le plus récent de la branche main si on n'a rien précisé).<br>
Pour sourcer cela il nous faut regarder directement dans le code d'uv depuis le repo git. Nous allons tâcher de donner le maximum de sources. Pour obtenir **\<repo_ident>** on part de la structure `GitUrl` dans le fichier `crates/uv-git-types/src/lib.rs` on récupère l'url du git puis on la transforme en une `RepositoryUrl` du fichier `crates/uv-cache-key/src/canonical_url.rs` et enfin on la hash avec le fonction `cache_digest<H: CacheKey>(hashable: &H) -> String` du fichier `crates/uv-cache-key/src/digest.rs`. Pour obtenir **\<short_commit_sha>** dans `crates/uv-git/src/source.rs` on récupère `actual_rev` qui est une `GitOId` du fichier `crates/uv-git-types/src/oid.rs`. cet Id est en fait le hash du commit que depuis lequel on veut télécharger le paquet. Puis grâce à `to_short_id(&self, revision: GitOid) -> Result<String>` du fichier `crates/uv-git/src/git.rs` on récupère la short id en question. <br>
Vous pouvez le tester en installant ce "faux pandas" sur le git que j'ai donné ci dessus en lançant `uv run --with git+https://gitlab.dsi.universite-paris-saclay.fr/matthieu.urios/testMaliciousPackage python`, puis en navigant dans votre cache uv dans /git-v0/checkout vous allez retrouver le paquet dans un dossier ayant pour nom un hash de l'url du git et à l'intérieur duquel il y aura un dossier ayant comme nom la shot id du dernier commit visible sur le git. <br><br>
Les paquets téléchargé depuis pypi quand à eux se retrouvent dans le bucket `archive-vX` dasn un dossier nommé par une chaîne de caractère que l'on pourrait penser être à première vue être un hash ed quelque chose. Cependant après investigation du code source d'uv, nous pouvons voir que dans le fichier `crates/uv-cache/src/archive.rs` cet id est ce qu'uv appelle une `uv_fastid::Id::insecure()`. Pour savoir ce que c'est allons voir dans le fichier `crates/uv-fastid/src/lib.rs` dans la classe `Id`. Nous nous rendons compte que la fonction `insecure() -> Self` de cette classe ne fait que créer un array aléatoire d'unsigned int de 8 bit puis le transforme en un array de caractère ASCII de l'alphabet défini dans le même fichier. Comme cet Id est générée aléatoirement uv doit bien le conserver quelque part s'il doit retrouver où sont les paquets dans le cache. <br>
Avant de préciser où il se trouve nous devons préciser que pour les paquets provennant de pypi, uv respecte les *HTTP caching headers*. On peut voir cela dans la documentation d'uv [ici](https://docs.astral.sh/uv/concepts/cache/#dependency-caching). <br>
Donc pour trouver cet Id nous devons nous rendre dans un autre bucket du cache uv : `wheels-vZ`. En naviguant dans ce dossier nous trouvons des dossier pour chacuns de nos paquets dont on à téléchargé la wheels sur pypi. Dans ces dossier nous pouvons retrouver des fichier en `.http`. Et c'est justement dans ces fichiers que se trouve l'ArchiveId. On peut le voir avec un simple `cat <nom du fichier>`. #### Qu'est ce qu'uv fait de tout cela et pourquoi il n'y a pas de risques :

Quand on se situe dans un projet uv (soit un environement virtuel créé avec uv), ce qui détermine où uv va chercher le paquet dans le cache est la chose suivant : l'index du paquet que l'on done dans le `pylock.toml` (voir doc astral [ici](https://docs.astral.sh/uv/concepts/indexes/#defining-an-index)).
Il est en effet possible de définir plusieur indexs pour la résolution des paquets avec différentes priorités. A savoir que l'index par défaut est celui de **pypi** et que dès qu'un autre index est spécifié il devient automatiquement le moins prioritaire. Quand on souhaite inclure un paquet à notre projet, afin de savoir si un paquet est déjà installé dans le cache uv va regarder cet index et prendre une décision en fonction de ce dernier. <br>
S'il s'agit d'un index pypi, uv va aller chercher dans le bucket `wheels-vZ` le dossier correspondant au paquet et regarder le fichier `.http`. Si la wheels est expirée, uv la retélécharge depuis la source d'où il l'a téléchargé précédement. Après avoir fait cette vérification (et retéléchargé la wheels si besoin) il va lier le dossier du bucket `archive-vX` où la wheels a été extraite au `.venv` du projet. <br>
S'il s'agit d'un index git, uv peut directement à partir de l'adresse donnée dans l'index retrouver dans le bucket `git-vY` où se trouve le paquet dans le cache et faire le lien avec le `.venv`. <br>

Les cas où un utilisateur innocent peut se retrouver à éxécuter du code malveillant sont donc les suivants :
- L'attaquant a un accès direct à l'environement de la victime et peux donc modifier son `pyproject.toml` afin que, par exemple, uv aille chercher dans le cache un faux pandas à la place du pandas pypi.
- L'attaquant à pu écrire sur le cache et placer du code vérolé dans le bucket `archive-vX` dans le dossier qu'uv pense être celui d'un paquet pypi.

Dans le premier cas s'il à accès à l'environement de la victime il peut simplement exécuter du code sans avoir à passer par notre cache partagé et il n'est donc pas mis en cause.
Dans le deuxième cas il suffit de garantir le fait qu'un attaquant ne pourra pas écrire sur le cache. Cela renforce bien evidement le fait que du code arbitraire ne doit pas pouvoir être exécuté lors de la construction d'un wheels venant d'une source distante, sinon un attaquant pourrait écrire sur notre cache et cette sécurité ne tiendrai plus.

Dans les autres cas les mecanismes d'uv que nous avons décrit ci - dessus garantissent que quand un utilisateur demande un certain paquet et que dans le `pyproject.toml` de son enviroment l'index pour aller chercher ce paquet et celui d'une source de confiance (pypi où une source que la personne en charge de la création de l'environement / une personne responsable de la sécurité). L'utilisateur est garantie d'avoir ce paquet et pas un autre dans son projet et donc ne se retourve pas à éxécuter du code malveillant.
